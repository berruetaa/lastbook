# Interface internationalization

Lastbook ships a reusable, synchronous and dependency-free translation engine.
It never opens a connection, reads browser storage, translates library material
or changes the user's documents. A host page chooses a locale, supplies trusted
local catalogs, and explicitly marks its own interface strings. English is the
reference catalog and the last fallback.

The first consumer is Setup: three static labels in `web/setup.html`. The rest
of Setup and other pages are **not yet translated**. The reusable APIs below are
available now for subsequent screens.

## Files and API

All JS files live directly in `web/` so the existing app packager includes them.
Load them in this order as classic local scripts:

```html
<script src="/ui/i18n-core.js"></script>
<script src="/ui/i18n-dom.js"></script>
<script src="/ui/i18n-catalogs.js"></script>
```

`createI18n({ catalogs, locale, fallbackLocale, fallbacks })` works without
the DOM or globals other than `Intl` and exposes:

- `t(key, params?)`: translated plain text, or `undefined` for an unknown key.
- `resolve(key, params?)`: `{ text, locale }` (the effective catalog language).
- `setLocale(locale)`: select a language explicitly.
- `chooseLocale(preferences)`: pick the first preference whose fallback chain
  reaches a populated catalog, **without** considering English until preferences
  are exhausted. Invalid preferences are ignored.
- `usePreferredLocales(preferences)`: choose and activate that preference.
- `number(value, options?)`, `date(value, options?)`: locale-aware formatting.
- `locale` and `supportedLocales`: current selection and available catalogs.

Locales use tags accepted by `Intl.getCanonicalLocales` (Unicode locale IDs,
which cover ordinary BCP 47 tags like `es-UY` and `fr-CA`, but not all private
or grandfathered BCP 47 tags). A route such as `{ es: ["es-419"] }` applies
after any exact regional catalog: `es-AR` → `es` → `es-419` → `en`.
Unexpectedly unsupported first preferences must not suppress later supported
preferences. The fallback chain also strips extensions such as `-u-nu-latn`.

Only first-party catalog objects are trusted input. The engine copies their own
data entries, rejects getters and invalid forms, and verifies that every
translated key and its placeholders match the English reference. Missing
translated keys transparently use the English catalog. Do not translate guide
content, URLs, source quotations or user-entered data.

## Add a language

1. Add a catalog to `web/i18n-catalogs.js`, using the existing English semantic
   keys, e.g. `fr: { "setup.title": "Configurer Lastbook" }`.
2. If a regional catalog is meant to serve every variant, add a route for its
   parent language (as Setup does for `es` → `es-419`). Otherwise keep the
   regional tag exclusive: an unrelated regional preference should be skipped.
3. Opt in to new strings by marking **leaf** text nodes with `data-i18n="key"`.
   Keep human-readable English text inside the HTML for no-JavaScript fallback.
   To preserve icons or other markup, mark a child `span`, not its parent.
4. For attributes use `data-i18n-aria-label`, `data-i18n-placeholder`,
   `data-i18n-title` or `data-i18n-alt`. The adapter uses `textContent` or
   `setAttribute`, never `innerHTML`, and sets `lang` to the actual catalog
   language of each translated element.
5. For dynamically created UI call `applyI18n(container, i18n)` after
   rendering. The adapter never observes or rewrites arbitrary DOM nodes.
   Avoid mixing fallback and translated attributes on one element when their
   spoken language would differ.
6. Add tests for the new language, including missing keys, plural grammar,
   interpolation, and at least one rendered interface label.

The Setup consumer in `web/setup-i18n.js` uses `navigator.languages` but does
not store a language preference yet. It exposes `LastbookI18n` on that page,
with `t`, `resolve`, `chooseLocale`, `number`, `date`, `apply`, `setLocale` and
`usePreferredLocales` for subsequent Setup code. When a settings selector is
added later, its owner should persist the selection and call `setLocale`; the
reusable core deliberately has no storage policy.

## Messages and formatting

```js
const i18n = createI18n({
  catalogs: {
    en: { hello: "Hello, {name}", files: { "=0": "No files", one: "{count} file", other: "{count} files" } },
    "es-419": { hello: "Hola, {name}", files: { "=0": "No hay archivos", one: "{count} archivo", other: "{count} archivos" } },
  },
  locale: "en", fallbackLocale: "en", fallbacks: { es: ["es-419"] },
});
i18n.usePreferredLocales(["es-UY", "en-US"]);
i18n.t("hello", { name: "Ana" });  // "Hola, Ana"
i18n.t("files", { count: 2 });     // "2 archivos"
i18n.number(1234.5);              // locale-specific number formatting
```

Plural `count` must be a finite number. Explicit forms like `"=0"` take
precedence on exact numeric equality. Other forms use `Intl.PluralRules` with
the effective catalog locale, and `{count}` uses `Intl.NumberFormat` with
the same locale and default rounding (at most three fraction digits). Thus
plural grammar always agrees with the displayed number, even for decimals.
Other placeholders accept only primitive strings, numbers or booleans. The
engine never interprets HTML; callers must also use text-only DOM sinks.

## Verification

```bash
node --test app/tests/i18n_core_test.cjs
python3 -B -m unittest app.tests.test_readable app.tests.test_bridge app.tests.test_setup app.tests.test_data_folder app.tests.test_what_ships app.tests.test_update app.tests.test_address_search app.tests.test_topic_search app.tests.test_chat_steps app.tests.test_validate_topics app.tests.test_libq app.tests.test_shell_macos
```

The app's own packaging scanner must include all local JS assets. Before a PR
is merged, check the three Setup labels and language attributes in a browser
or native WebView (including light/dark mode). The tests cover runtime logic
and opt-in bindings but do not replace native-platform smoke checks.
